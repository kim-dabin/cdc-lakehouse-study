## 원천 모델

테이블마다 PK, FK, 변경 가능한 컬럼, 삭제 의미를 적는다. 수정 또는 삭제가 실제로 발생하는 테이블을 하나 이상 포함한다. 외부 데이터만 있다면 서비스 변경을 재현할 PostgreSQL 테이블과 이벤트 생성기를 설계한다.

## 데이터 흐름

내 아키텍처, Bronze 원문 예시, Silver 키와 최신 버전 판별 기준, Gold 모델 의존 관계를 작성한다.

### 개인 테이블을 연결할 때 확인할 곳

공통 실행 도우미는 주문·결제·환불 예제용이다. 개인 설계서나 DDL을 추가하는 것만으로 새 테이블의 수집과 마트가 자동으로 연결되지는 않는다. 3회차에는 테이블과 변경 의미를 정하고, 아래 연결은 후속 구현에서 확인한다.

| 연결 지점 | 개인 도메인에 맞출 내용 |
|---|---|
| 원천 테이블·변경 입력 | DDL·PK/FK·수정/삭제 사례, 이전 값이 필요한 범위의 replica identity, publication 대상과 개인 예제 생성기 |
| Debezium | `scripts/configure.py`의 포함 테이블과 publication 설정 |
| Kafka·Flink | 테이블별 토픽과 `flink/ingest.sql.template`의 topic-pattern, Bronze 입력 범위 |
| Silver | `scripts/pipeline.py`의 MODELS·업무 키·컬럼·최신 판단·삭제 처리 |
| dbt | sources와 모델·지표 정의·테스트의 테이블 및 컬럼 참조 |

수집 중인 공통 환경에 설정을 바로 덮어쓰지 않는다. 개인 환경에서 연결 범위를 맞추고, 같은 키의 신규·수정·삭제가 각 계층에서 기대한 결과로 이어지는지 확인한다.

공통 예제의 과거 이벤트 재전달은 원래 `source.lsn`과 before/after를 보존한 이벤트를 사용한다. 나중에 받은 Kafka offset만으로 업무 버전이 새롭다고 판단하지 않는다. 버전 정보가 빠지거나 해석되지 않는 입력은 별도 검증 사례로 두고, 오류 처리 기준을 정한다. 공통 구현의 LSN·offset 규칙은 단일 원천·고정 토픽의 단일 파티션 범위다.

## 개선 전후

데이터 건수, 자원, 체크포인트 간격, 실행 주기와 측정 방법을 함께 기록한다. 결과에 영향을 주는 조건을 같게 둔다. 단일 측정값을 서비스 SLA로 표현하지 않는다.

코드, 실행 순서, 아키텍처, 지표 정의, 예상값과 실제값 비교, 실패·복구 기록을 제출한다. 8회차는 구현과 검증을 마무리하는 시간이며 발표는 별도 일정이다.
