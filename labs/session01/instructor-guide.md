# 1회차 강사용 진행안 — 변경 데이터 수집과 파이프라인 설계

총 120분. 강사는 맥미니에서 실행하고 학생은 로컬 SQL과 설계서를 작성한다. 개인 프로젝트 원천 명세, 수집 경로와 검증 기준을 만든다. Kafka·Spark·Docker 기초를 다시 설치하는 시간은 배정하지 않는다.

## 00:00–00:10: 데이터 엔지니어가 확인할 결과

“DB에 UPDATE가 성공했습니다. Flink도 RUNNING입니다. Iceberg까지 같은 변경이 도착했다고 말할 수 있을까요?”

학생에게 필요한 근거를 받는다. 원천 행, 실제 Kafka 메시지, Bronze의 동일 이벤트를 대조해야 한다. 오늘은 합성 데이터의 같은 refund_id에 c/u/d를 만들며, 세 변경이 빠짐없이 기록되는지를 확인한다. 마트 집계는 이후 회차로 연결한다.

## 00:10–00:30: 아키텍처 세 장

데이터 흐름 7분, 저장·메타데이터 6분, 실행 환경 4분, 역할 질문 3분.

- Flink는 CDC 원문을 Bronze에 append한다. 현재 상태의 upsert를 여기서 수행한다고 설명하지 않는다.
- MinIO 파일과 Catalog 위치 정보, Flink 복구 상태를 구분한다.
- 기존 Spark와 새 dbt의 역할은 후속 단계로 설명한다. dbt는 SQL 모델과 의존성·테스트를 관리하며 Spark가 실행한다.
- 학생은 SSH 접속하지 않는다. 강사 노트북 화면과 맥미니 런타임의 경계를 설명한다.
- 그림에 남은 100000/80000/70000은 전체 프로젝트의 후속 마트 예시다. 오늘의 수집 성공 기준은 c/u/d 이벤트 대조다.

## 00:30–00:45: 원천 명세와 변경 SQL

5분 PK/FK와 한 행의 의미, 7분 학생 DML 작성, 3분 예상값 검토.

orders·payments는 준비 데이터이며 핵심 관찰 대상은 같은 refunds 한 행이다. UPDATE는 20000에서 30000으로 정정하고 DELETE는 해당 행을 제거한다. 학생에게 WHERE 대상과 FK를 설명하게 한다. `REPLICA IDENTITY FULL`이 before 값을 제공하는 예제 전제임을 짚는다. WAL 내부·복구 알고리즘은 후속 회차에 다룬다.

## 00:45–01:10: 원천·Kafka·Bronze 시연

준비 행 3분, INSERT 7분, UPDATE 7분, DELETE 8분. [runbook](runbook.md)을 따른다.

각 변경에서 SQL 실행 → source-rows → kafka → wait → collect-check 순서로 본다. Kafka를 먼저 보여준 뒤 Bronze가 보일 때까지 기다린다. 학생은 키·op·before/after를 예상값과 대조한다. 같은 Kafka 위치가 Bronze에 남는지 출력의 checks를 확인한다. refresh와 Gold check는 핵심 시연에서 사용하지 않는다.

DELETE 후 원천 0행과 Bronze c/u/d 이력 세 행을 확인한다. Kafka의 null tombstone이 보이면 Bronze의 null 제외 설정을 설명한다. tombstone을 원천 비즈니스 삭제 이벤트와 합쳐 같은 행 수를 기대하지 않는다.

## 01:15–01:30: 수집 검증과 지연

5분 수집 대조, 5분 누락·중복 사례 판단, 5분 지연 기록과 한계.

- PK별 여러 이벤트는 정상 변경 이력일 수 있다.
- 같은 (topic,partition,offset)의 여러 Bronze 행과 다른 offset의 재전달은 구분해서 조사한다.
- offset은 파티션 내 위치이며 전역 순서를 뜻하지 않는다.
- wait는 대기 명령 시작 이후 첫 관찰까지의 시간이다. kafka_ts/ingested_at만으로 최종 commit 지연을 재현했다고 주장하지 않는다.
- 오늘 확인한 한 키의 세 이벤트는 전체 무누락·복구·exactly-once 보장 근거가 아니다.

“원천만 바뀐 경우와 Kafka까지 도착한 경우에 조사 순서가 어떻게 달라지나요?”를 학생에게 묻는다.

## 01:30–01:55: 개인 설계

5분 수집 범위·목적, 8분 원천 명세·경로, 7분 DDL·변경 테스트, 5분 검증·장애 조사 계획.

강사는 데이터 소비 목적, 테이블 2–3개, 한 행과 PK, 수정·삭제 의미, 원천부터 Bronze까지 목표 지연을 확인한다. publication/connector include list/Flink 토픽 패턴을 맞춰야 한다는 설정 과제를 남긴다. 재처리·복구 기능은 오늘 완성시키지 않고 필요한 기록과 검증 기준을 설계한다.

## 01:55–02:00: 종료와 제출

“수집됐다는 근거”, “원천 삭제 뒤 Bronze 이력이 남는 이유”, “내 프로젝트의 키와 검증 방식”을 학생이 자기 말로 적는다. student-worksheet.sql과 submission.md 제출. 나머지 DDL·DML·기대 이벤트는 다음 회차 전 완성한다.

## 시간이 밀릴 때

서버 문제가 5분 넘으면 같은 장애를 계속 디버깅하지 않는다. 실제 실행을 멈추고 과거 리허설 기록임을 명시해 해당 증거를 보여준다. 학생은 예상 이벤트와 개인 설계를 계속한다. 개인 설계 25분을 유지하고 세부 설정 설명을 줄인다. 마트 갱신·집계 SQL은 핵심 120분에 다시 넣지 않는다.
