# 1회차 강사용 진행안 — 120분

## 수업 목표

학생이 결제·환불 예제에서 원천 변경 → 변경 이력 → 현재 상태 → 분석 지표를 설명하고, 자기 프로젝트의 지표 하나와 원천 테이블을 설계한다. Kafka·Spark·Docker 기초 설명은 이미 들은 내용을 짧게 연결하는 정도로 진행한다.

진행 방식은 **강사 맥미니 시연 + 학생 노트북의 SQL·설계서 작성**이다. 학생에게 SSH 접속이나 서버 설치를 요구하지 않는다. 수업 시작 전에 이미지 다운로드, 서비스 기동, 시나리오 리허설을 끝낸다. [실행 순서](runbook.md)를 별도 터미널에 열어둔다.

총 120분. 정식 프로젝트 발표는 스터디 이후 별도 일정이다. 마지막 10분은 설계 점검과 다음 회차 안내다.

## 00:00–00:10 — 문제가 생기는 순간부터 시작

화면에는 숫자 세 개만 보여준다: 결제 100,000원 / 환불 20,000원 / 대시보드 100,000원.

> “결제는 10만원인데 2만원이 환불됐습니다. 지금 이 주문의 순결제액은 얼마여야 할까요? 원천 DB는 바뀌었는데 대시보드가 그대로라면 어느 구간을 먼저 확인해야 할까요?”

8만원이라는 답을 받은 뒤 허용 지연을 묻는다. 운영 중 취소 추이를 보고 싶은 경우와 다음 날 정산하는 경우의 차이를 학생이 설명하게 한다. 실시간의 기준은 ‘무조건 0초’가 아니라 이 지표를 사용하는 사람이 허용하는 지연으로 정한다.

## 00:10–00:25 — 전체 아키텍처

[프로젝트 그림](diagrams/project-architecture.png)을 기준으로 세 번 설명한다.

1. 데이터 경로: PostgreSQL → Debezium → Kafka → Flink → Iceberg Bronze → Spark SQL Silver → dbt Gold.
2. 저장 내용: Bronze에는 변경 이력, Silver에는 최신 상태, Gold에는 정의한 집계 결과가 있다.
3. 운영 경로: 같은 Iceberg Catalog와 저장소를 Flink/Spark가 사용하고, Airflow는 이후 회차에서 Silver·Gold 갱신을 주기 실행한다.

질문:

- “UPDATE가 들어오면 과거 기록은 어디에 남고 최신 금액은 어디에서 읽을까요?”
- “dbt가 Spark를 대신 실행하는 엔진일까요?” → dbt는 모델 SQL과 의존성·테스트를 관리하고 Spark가 SQL을 실행한다.
- “Flink 작업이 RUNNING이면 Gold도 최신일까요?” → 각 계층의 조회 결과로 확인해야 한다.

WAL 내부 구조, checkpoint 알고리즘, Iceberg manifest 구조는 다음 회차에 다룬다. 오늘은 역할과 조회 결과를 연결한다.

## 00:25–00:35 — 지표와 원천 모델

`sql/01-source.sql` 또는 [ERD](architecture.md)를 연다.

- 주문 한 건에 결제가 여러 번 발생할 수 있다.
- 환불은 어떤 결제를 돌려주는지 `payment_id`로 식별한다.
- 이 예제의 순결제액은 결제 성공액에서 환불 성공액을 뺀 값이다.
- 주문일 기준으로 묶으며 시간대는 Asia/Seoul이다. 환불 발생일 매출이나 회계상 매출이라는 이름을 붙이지 않는다.
- 예제 주문일은 고정된 테스트 값이다. 강의 일정과 관계없는 합성 데이터다.

> “테이블 한 행은 무엇을 뜻하나요? 같은 대상을 다시 수정할 때 어떤 키를 찾나요?”

학생이 키와 한 행의 의미를 말할 수 있어야 다음 단계로 넘어간다.

## 00:35–01:05 — 첫 입력과 환불

학생에게 `student-worksheet.sql`의 A/B를 작성하게 한다. 모든 SQL을 서버에 실행하는 방식 대신 1–2개의 답안을 검토해 화면에서 함께 수정한다. 실행은 강사용 SQL 파일과 회차별 namespace를 사용한다.

[runbook.md](runbook.md)의 결제 → 대기 → Bronze → 갱신 → 확인 순서를 실행한다. 결제 10만원이 세 계층에 보인 뒤 환불 2만원을 입력한다.

환불 후 **갱신 전에 layers를 먼저 보여준다**. 수업에서는 Airflow를 중지했으므로 원천은 8만원, Gold는 아직 10만원이어야 한다. Bronze에서 환불 이벤트를 확인한 뒤 수동 갱신하고 8만원을 보여준다.

> “수집은 정상인데 지표가 예전 값일 수도 있네요. 이때 수집기를 다시 켜는 게 해결책일까요?”

중간 확인값을 학생 가이드의 관찰표에 적게 한다. 조회 대기 시간을 채우기 위해 로그 화면만 오래 보여주지 말고, 학생의 원천 SQL을 함께 검토한다.

## 01:10–01:25 — 환불 정정

학생에게 먼저 계산하게 한다. “2만원 환불을 3만원으로 정정했습니다. 순결제액은 5만원일까요, 7만원일까요?”

같은 `refund_id`의 UPDATE이므로 환불 총액은 3만원, 순결제액은 7만원이다. Bronze에서 c/u 두 이벤트와 before=20000 / after=30000을 보여준다. 갱신 후 Silver 한 행과 Gold 7만원을 확인한다.

DELETE는 시간이 남을 때 2회차 예고로만 시연한다. 핵심 진도가 늦어지면 생략한다.

## 01:25–01:50 — 개인 프로젝트 설계

한 번에 전체 플랫폼을 만들겠다는 목표를 지표 하나로 좁힌다. 예약 취소율, 출고 대기 건수, 구독 활성 건수 등에서 학생이 직접 선택한다. 결제 예제를 반드시 프로젝트로 사용할 필요는 없다.

피드백 순서:

1. 누가 어떤 판단을 하려고 지표를 보는가?
2. 한 행은 무엇이고 PK는 무엇인가?
3. 어떤 수정/삭제가 그 지표를 바꾸는가?
4. 원천에서 바뀐 뒤 몇 분 안에 반영해야 하는가? 왜인가?
5. 2–3개 테이블과 지표 하나로 8회 안에 검증할 수 있는가?

DDL 전체 완성을 목표로 하지 않는다. 관계 초안과 테이블 하나의 DDL을 수업 중 작성하고 나머지는 회차 사이에 완성한다.

## 01:50–02:00 — 마무리 확인

학생마다 다음 세 문장을 채워 제출한다.

- “Bronze에는 ___가 남고, Silver에는 ___가 남습니다.”
- “원천 DB가 바뀌었는데 Gold가 그대로라면 ___를 확인하겠습니다.”
- “내 프로젝트에서는 ___가 바뀌면 ___ 지표가 바뀌어야 합니다.”

1회차 통과 기준은 서버를 설치했는지가 아니라, 예제 결과를 설명하고 자기 프로젝트의 변경 시나리오를 정의했는지다.

## 시간이 밀릴 때

- 15분 지연: 삭제 예고를 생략하고 개인 설계 25분은 유지한다.
- 서버 지연: 5분 이상 같은 장애를 실시간 디버깅하지 않는다. 리허설 기록을 보여주고 학생 SQL/설계로 전환한다. 녹화·기록은 실시간 실행과 구분해 말한다.
- 학생 SQL이 느림: INSERT/UPDATE 작성은 유지하고 복잡한 원천 집계 SELECT는 강사용 정답을 함께 읽는다. 숙제로 다시 작성한다.
