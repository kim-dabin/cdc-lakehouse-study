# CDC를 배우는 이유와 개인 프로젝트

서비스 DB의 데이터는 입력한 뒤에도 바뀝니다. 예약이 취소되고, 배송지가 정정되고, 상품이 삭제됩니다. 데이터 엔지니어는 이런 변경을 필요한 곳에 전달하면서 현재 상태와 변경 이력을 함께 관리합니다. CDC(Change Data Capture)는 DB의 변경을 포착하는 방식이며, 이 변경을 필요한 곳에 전달하는 수집 경로를 설계할 때 사용합니다.

## 왜 주기적으로 테이블을 복사하는 것으로 부족할까요?

배치 전체 복사는 정해진 시점의 상태를 가져오는 데 유용합니다. 다만 데이터가 많아질수록 같은 행을 반복해 읽고 전송하며, 다음 배치까지 목적지 데이터가 과거 상태로 남을 수 있습니다. 하루 단위 보고서처럼 긴 지연을 허용하면 배치가 충분할 수도 있습니다.

`updated_at`을 조건으로 변경분을 읽는 방식도 가능합니다. 하지만 실제로 지운 행을 별도로 추적하고, 같은 시각의 변경·조회 경계·중간 상태를 처리할 규칙이 필요합니다. 두 번의 조회 사이에 예약이 확정됐다가 취소되면 마지막 상태만 읽어 그 사이 변경을 놓칠 수 있습니다.

이 스터디의 로그 기반 CDC는 PostgreSQL의 WAL에서 변경을 읽고 입력·수정·삭제를 이벤트로 전달합니다. 초기 데이터는 스냅샷으로 읽고 그 뒤의 변경을 이어받는 구조를 다룹니다. Kafka에 전달한 변경을 Flink로 Iceberg Bronze에 보관하면 원천에서 삭제한 행의 변경 기록도 다시 확인할 수 있습니다. [Debezium 공식 설명](https://debezium.io/documentation/reference/stable/features.html).

다만 CDC가 원천 부하나 운영 비용을 없애지는 않습니다. 초기 스냅샷의 읽기 부하, WAL 보존, connector 지연, Kafka 보존 기간, 목적지 commit과 복구를 관리해야 합니다. 수집만 빨라졌다고 분석 테이블까지 즉시 최신이 되는 것도 아닙니다. API 데이터나 사용자 클릭처럼 DB 변경에 없는 이벤트는 별도 수집 경로가 필요합니다.

## 채용공고에서 CDC 경험을 확인하는 이유

실시간 수집·데이터 플랫폼 직무에서는 서비스 DB의 변경을 지연과 누락을 관리하며 목적지로 전달해야 합니다. 그래서 CDC 기술명과 함께 Kafka·분산 처리, 파이프라인 설계·운영, 장애 대응 경험을 확인합니다. 이는 아래 공식 공고에서 확인한 업무를 바탕으로 한 해석입니다. 채용시장 전체에서 요구 비율이 늘었다는 통계를 뜻하지 않습니다.

- [토스뱅크 Data Platform Engineer (Streaming)](https://toss.im/career/job-detail?job_id=6603749003)는 CDC·Kafka Connect·Flink로 실시간 파이프라인을 구축한 경험을 요구하며, 트러블슈팅과 운영 결과도 설명하도록 안내합니다. 3년 이상 관련 경험 선호가 있는 경력 공고입니다.
- [CJ대한통운 TES 데이터 엔지니어](https://recruit.cj.net/recruit/ko/recruit/recruit/bestDetail.fo?direct=N&zz_jo_num=J20260629039137)는 CDC를 포함한 수집 경로의 설계·운영과 성능 진단을 업무로 제시합니다. 최소 경력 5년이며 기술 선택 이유도 묻습니다. CDC라는 단어가 업무에 있다는 이유로 필수 자격이라고 바꿔 해석하지 않습니다.
- [신한투자증권 데이터 엔지니어](https://recruit.shinhaninvest.com/recruit/view.do?annoId=4050724)는 Iceberg와 CDC 관련 지식을 자격요건에 적었습니다. 관련 경력 3년 이상이며 **2026-02-22 마감된 공고**입니다. 최근 연도의 요구 역량 사례로만 사용합니다.

2026-10-15에 공식 페이지 본문을 확인했습니다. 공고가 모든 신입에게 같은 수준을 요구한다는 뜻은 아닙니다. 수업에서는 경력자의 운영 책임을 개인 프로젝트 규모로 줄여 경험합니다. 본문 강의는 회사별 취업 전략보다 어떤 업무 문제를 해결하는지 설명하고, 회사명과 출처는 참고 자료로 제공합니다. ML 관련 업무는 수업 범위에 넣지 않습니다.

## 이미 배운 Kafka·Spark와 무엇이 연결되나요?

Kafka에 임의 메시지를 보내는 단계에서 원천 DB 변경을 수집하는 단계로 넓어집니다. Spark로 파일을 가공하는 경험은 변경 이력을 키별 현재 상태로 만드는 작업으로 이어집니다. S3·Docker·Airflow·GitHub 경험은 저장소, 실행 환경, 반복 실행과 검증 자료 관리에 사용합니다. Flink·Iceberg는 계속 들어오는 변경을 커밋하고 여러 엔진에서 읽을 테이블로 보관하는 데 연결합니다.

프로젝트에서 설명할 것은 선택 이유와 결과입니다. 어떤 PK와 이벤트를 보관했는지, 수정·삭제가 어떻게 반영되는지, 재처리 뒤에도 결과가 같은지, 얼마나 늦게 도착하며 어디가 지연되는지를 코드와 기록으로 보여줍니다. 1회차에는 그중 원천·Kafka·Bronze 대조와 개인 설계 초안을 만듭니다.

## 만들 수 있는 프로젝트

아래는 수업용 제안입니다. 특정 회사가 이 구조로 운영한다는 사례가 아닙니다. 원천 데이터는 학생이 PostgreSQL에 합성 데이터로 만들 수 있습니다. 하나를 선택해 원천 테이블 2–3개부터 시작합니다.

### 1. 예약 변경 이력과 현재 상태 파이프라인

- 문제: 예약이 확정된 뒤 시간이 바뀌거나 취소돼도 목적지에는 예전 정보가 남습니다.
- 원천: `customers`, `reservations`. 예약의 PK는 `reservation_id`입니다.
- 구현: CDC 원문을 Bronze에 보관하고 Silver에는 예약별 최신 상태를 구성합니다. 상태 변경과 실제 DELETE를 구분합니다.
- 검증: 같은 예약의 확정·일정 정정·취소를 수집하고, 원천 행과 최신 상태를 대조합니다. 예전 이벤트를 재전달해도 상태가 되돌아가지 않는지는 이후 회차의 확장 실험입니다.
- 산출물: 원천 명세, 변경 fixture, 수집 대조표, 최신 상태 테이블과 검증 기록.

### 2. 물류 상태 동기화 파이프라인

- 문제: 배송 상태와 도착 예정일이 수정될 때 집계용 데이터가 뒤늦게 바뀝니다.
- 원천: `shipments`, `shipment_items`. `shipment_id`를 기준으로 변경을 추적합니다.
- 구현: 상태 변경 이력과 배송별 현재 상태를 분리하고 Kafka·Bronze 수집 위치를 보관합니다.
- 검증: 출고 대기·출고 완료·예정일 정정이 같은 키로 수집되는지 확인합니다. 이전 버전 재전달이 최신 상태를 덮지 않는지 후속 회차에서 검사합니다.
- 산출물: 수집·저장 경로, 상태 변경 이력, 원천 대조와 지연 관찰 기록.

### 3. 상품 정보 레이크 구축

- 문제: 상품명·판매 상태·가격이 바뀌거나 상품이 삭제될 때 파일을 다시 모으는 방식으로는 변경 추적이 어렵습니다.
- 원천: `products`, `prices`. 원천 테이블의 실제 PK와 상품 연결 키를 구분합니다.
- 구현: 상품·가격 변경을 수집해 Iceberg 이력과 현재 상태를 구성합니다. 삭제 상품을 어떻게 표시할지 정합니다.
- 검증: 가격 정정, 판매 중지 UPDATE, 실제 DELETE의 서로 다른 이벤트를 확인합니다. 필드 추가는 선택 확장 실험입니다.
- 산출물: 수집 범위, 이력·현재 상태 테이블, 삭제 처리와 데이터 품질 검증. 고객용 최저가 검색 서비스는 범위에 넣지 않습니다.

### 4. 구독 상태 변경 파이프라인

- 문제: 가입·기간 정정·해지 후에도 downstream에 예전 상태가 남습니다.
- 원천: `subscriptions`, `invoices`.
- 구현: 상태와 기간의 변경 이력을 적재하고 키별 현재 상태를 만듭니다. 시간이 지나면 만료되는 상태는 DB 변경이 없으면 CDC 이벤트도 발생하지 않으므로 별도 계산·스케줄이 필요합니다.
- 검증: 기간 정정·해지·복구 시나리오와 입력 이벤트의 중복 처리를 구분합니다.
- 산출물: 상태 정의, 원천 변경 테스트, 현재 상태 대조와 재처리 기록.

### 5. 결제·환불 정정 파이프라인

- 문제: 이미 수집한 환불 금액이 정정되거나 이벤트가 재전달됩니다.
- 원천: `payments`, `refunds`와 선택적으로 `orders`.
- 구현: 환불 키·원천 버전·수집 위치로 변경 이력을 보관하고 현재 상태를 구성합니다.
- 검증: 환불 입력·금액 정정·삭제, 중복 재전달을 각각 실행해 원천과 목적지를 대조합니다. Gold는 이후 회차에 검증용 활용 테이블로 추가합니다.
- 산출물: c/u/d 증거, 현재 상태 테스트, 중복·재처리 실험 리포트. 이번 1회차의 강사 예제와 같은 도메인을 선택할 필요는 없습니다.

## 8회 안에 완성할 범위

공통 핵심은 원천 명세·DML, CDC 수집, Bronze 이력, Silver 현재 상태, 후속 활용 테이블, 데이터 대조와 복구 기록입니다. 역순 이벤트·스키마 변경·성능 튜닝을 모두 처음부터 목표로 잡지 않습니다. 기본 경로를 검증한 뒤 자신의 주제에 필요한 확장 실험을 선택합니다.

1회차에는 프로젝트 하나를 고르고, 왜 이 데이터에 CDC가 필요한지와 입력·수정·삭제의 기대 결과를 적습니다. 최종 포트폴리오에는 실행 코드뿐 아니라 설계 이유, 검증 SQL과 실제 관찰 기록이 남아야 합니다. 수업 규모의 경험과 실제 대규모 운영 경험은 구분해서 설명합니다.

## 프로젝트별 최소 완성 범위와 선택 확장

모든 주제의 기본 범위는 원천 c/u/d, Bronze 이력, Silver 현재 상태, 간단한 후속 활용 테이블과 테스트다. 후속 활용은 ML 없이 진행하며 기본 경로를 확인한 뒤 아래 확장을 하나 선택한다. 회차별 진도는 프로젝트에 맞춰 조정한다.

| 주제 | 최소 완성 범위 | 선택 확장 하나 |
|---|---|---|
| 예약 | 예약 키별 일정·취소 이력과 현재 상태, 논리 취소와 DELETE 구분 | 예전 이벤트 재전달 뒤 최신 상태 유지 |
| 물류 | shipments 헤더의 상태·예정일 변경과 현재 상태 | items 조인 기반 완료 여부 활용 테이블 |
| 상품·가격 | products/prices의 PK·관계, 정정·판매 중지·삭제 반영 | 새 컬럼 추가 뒤 Bronze·Silver 반응 관찰 |
| 구독 | 명시적 가입·기간 변경·해지 수집과 현재 상태 | DB 변경 없는 시간 만료를 주기 계산 |
| 결제·환불 | 부분 환불 추가와 기존 환불 정정 구분, 이력·현재 상태·활용 테이블 대조 | 중복 재발행 또는 복구 뒤 결과 동일성 |

상품 가격을 같은 행에 덮어쓸지 price_id별 정책 행으로 추가할지 먼저 정한다. 물류의 아이템별 부분 배송은 기본 범위에 넣지 않는다. 구독 만료는 날짜가 지났다는 이유만으로 CDC가 발생하지 않는다.

**1회차에는 핵심 변경 테이블 하나와 DDL·기대 이벤트까지만 필수**다. 나머지 명세와 개인 DML은 다음 회차 전 과제로 확장한다.
