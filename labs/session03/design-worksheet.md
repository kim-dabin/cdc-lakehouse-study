# 3회차 설계 학습지

설명을 들으며 한 줄씩 적고 마지막 개인 작업 30분에 도메인·원천 테이블·적재할 정보를 확정합니다. 별도 DDL 구현이나 새 제출 문서를 만드는 양식은 아닙니다. 아직 근거가 없는 규칙은 질문으로 남기고 설계 목표·예상·실제 관찰을 구분합니다.

## 작성 예시 — 공간 예약

아래는 **가상의 설계 예시**입니다. 지연 수치는 수업 환경의 실측·보장이 아니며 그대로 구현해야 하는 공통 정답도 아닙니다.

| 항목 | 작은 예시 |
|---|---|
| 업무 질문 | 운영자가 취소 후 다시 예약 가능한 공간과 유효 예약 수를 알고 싶습니다. |
| 두 지연 목표 | 원천 변경부터 Bronze 이력 확인 1분, 유효 예약 수 반영 10분을 잠정 목표로 잡습니다. |
| 테이블·키 | rooms(room_id PK), reservations(reservation_id PK, room_id FK). 방 하나에 여러 예약이 연결됩니다. |
| 취소와 삭제 | 취소는 status를 CANCELLED로 수정합니다. 행을 지우는 물리 삭제와 의미를 나눕니다. |
| 원문 보존 이유 | 취소·시간 변경의 경위와 다시 계산할 입력을 남깁니다. |
| 선택과 비용 | 지속 수집 경계를 보기 위해 Flink를 쓰되 별도 엔진·checkpoint·파일 관리를 맡습니다. 배치로 충분한지 먼저 비교합니다. |
| 재전달 기대값 | 같은 취소가 다시 와도 유효 예약 수를 한 번 더 줄이지 않습니다. |
| 확인 근거 | 특정 reservation_id의 현재 status와 해당 room_id의 유효 예약 수를 각각 조회합니다. |
