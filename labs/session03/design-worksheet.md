# 3회차 설계 학습지

공통 예제를 함께 보며 한 줄씩 적고, 수업 말미 개인 작업 30분에 **각자의** 도메인·원천 테이블·적재할 정보를 확정합니다. 별도 DDL 구현이나 새 제출 문서를 만드는 양식은 아닙니다. 아직 근거가 없는 규칙은 질문으로 남기고 설계 목표·예상·실제 관찰을 구분합니다.

## 먼저 다룰 공통 예제 — 주문·결제·환불

제공된 `orders`·`payments`·`refunds`로 수집·적재를 확인한 뒤 아래 개인 설계에 적용합니다. 공통 예제는 작성 방법과 판단 기준을 보여주기 위한 것이며, 개인 프로젝트의 주제를 주문으로 통일하지 않습니다.

| 항목 | 작은 예시 |
|---|---|
| 업무 질문 | 결제 100,000원에 대한 환불이 20,000원에서 30,000원으로 정정되고 철회됐을 때, 현재 환불 상태와 변경 경위를 구분할 수 있나요? |
| 두 지연 목표 | 원천→Bronze 이력 확인과 원천→최종 지표 반영을 따로 정합니다. 관찰 시작부터 첫 조회까지 잰 값은 원천 commit부터의 지연과 구분합니다. |
| 테이블·키 | orders(order_id PK) → payments(payment_id PK, order_id FK) → refunds(refund_id PK, payment_id FK). |
| 변경과 삭제 | refunds INSERT 20,000원 → UPDATE 30,000원 → DELETE. 이 예제의 물리 삭제는 환불 철회를 뜻합니다. |
| 원문 보존 이유 | 원천 환불 행이 사라져도 c/u/d 경위와 다시 해석할 입력을 남깁니다. |
| 선택과 비용 | raw 원문과 전달 위치를 Flink로 계속 append합니다. 대신 엔진·checkpoint·파일·commit을 운영하며 단순한 대안과 비교합니다. |
| 재전달 기대값 | 같은 입력을 다시 처리해도 후속 Silver의 현재 환불 상태와 Gold 지표를 한 번 더 차감하지 않아야 합니다. Bronze raw append 자체가 업무 중복 제거를 한다는 뜻은 아닙니다. |
| 확인 근거 | 같은 refund_id의 원천 행 1→1→0과 Bronze 이력 1→2→3, Kafka 전달 위치·checkpoint·commit·같은 키 SELECT를 구분해 대조합니다. |

공통 예제 실행은 [개인 실행 안내](../../docs/self-study.md)를 따릅니다. 수업에서는 강사 공유 화면에서 예측·SQL·결과 대조를 진행하고, 개인 환경에서는 같은 예제를 실행합니다. 아래부터는 자신의 도메인으로 작성합니다.

- 후속 Silver·Gold에서 테이블을 연결·집계할 키 한 줄:

중복 제거 키·최신 버전 기준은 **4회차 Silver MERGE**, 지표·조인 키와 기대값은 **5회차 dbt Gold 테스트**, 변경·삭제 정책과 과거 정정 사례는 **6회차 소급 정정**에 이어서 사용합니다. 새 항목을 따로 작성하기보다 위에 정한 내용을 연결합니다.
