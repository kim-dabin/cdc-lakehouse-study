# 3회차 가이드 — Flink → Bronze 적재 심화, 개인 도메인·테이블 설계 확정

**120분 · 강사 맥미니 시연 + 학생 설계·예측·리뷰**

지난 시간에는 같은 변경을 원천·Kafka·Bronze에서 찾아봤습니다. 이번에는 Flink SQL을 읽으며 Kafka 원문과 전달 정보를 어떻게 받아 Bronze 이력으로 남기는지 확인합니다. 어떤 변경을 왜 보존해야 하는지, 이력과 현재 상태를 어느 계층이 맡을지 판단한 뒤 각자의 도메인과 원천 테이블 설계를 확정합니다.

[설계 학습지](design-worksheet.md)를 처음부터 열어두세요. 초반에 도메인 한 줄을 정하고 각 설명 뒤에 내 프로젝트의 선택을 짧게 적습니다. 개인 작업 시간에는 테이블·키·변경 의미와 Bronze에 보존할 정보를 확정합니다. 실제 DDL을 완성하거나 강사의 실행 명령을 전부 따라 치는 시간은 아니며, 수업 중 별도 `submission.md`를 작성하지 않습니다.

## 준비할 것

- 설계 학습지를 편집할 도구와 강사 공유 화면.
- 지난 복습에서 확인한 결과·막힌 지점·질문.
- 관심 있는 업무 하나. 아직 정하지 못했다면 공간 예약·구독·물류·재고 중 하나로 시작해도 됩니다.

수업 중 실험은 강사가 맥미니에서 실행합니다. 학생은 실행 전에 예상하고, 나온 증거가 무엇을 뜻하는지 읽고, 내 설계에 반영할 판단을 남깁니다. 개인 환경에서 공통 동작을 확인하는 방법은 [별도 실행 안내](../../docs/self-study.md)에 있습니다.

## 1. 업무 질문과 변경 요구사항

먼저 “누가 이 데이터를 보고 어떤 결정을 내리는가”를 한 문장으로 적습니다. 취소된 예약이 계속 유효 예약 수에 남으면 어떤 판단이 달라질까요? 내 주제에서도 수정·삭제가 반영되지 않았을 때 생기는 일을 찾습니다.

지연 목표는 두 개로 나눕니다.

- **원천 변경부터 Bronze 조회:** 변경 이력이 어느 정도 안에 확인되어야 하나요?
- **원천 변경부터 최종 지표:** 업무에 사용할 값은 어느 정도 안에 바뀌어야 하나요?

예제의 checkpoint 간격이나 마트 실행 주기를 목표로 그대로 복사하지 않습니다. 필요한 이유부터 적고 수치가 아직 미정이면 확인할 정보를 남깁니다. 이 단계에서는 운영 환경에서 달성했다고 주장하는 것이 아니라 설계 목표를 정합니다.

원천 테이블의 PK, 수정 가능한 컬럼, 삭제 의미도 적습니다. 취소가 상태 변경인지 물리 삭제인지 구분합니다. 같은 변경이 다시 들어왔을 때 현재 값이나 지표가 어떻게 유지되어야 하는지도 생각합니다.

전체 배치·수정 시각 기반 증분·로그 CDC 중 내 요구사항에 맞는 방식을 짧게 비교합니다. CDC의 WAL 보존·커넥터 운영, Kafka의 이벤트 보관·소비자 분리에는 이점과 비용이 함께 있습니다. 배운 도구라서 넣기보다 필요한 이유 한 가지와 감수할 부담 한 가지를 남깁니다.

## 2. Flink 입력·출력과 저장 경계 읽기

### Flink가 Kafka에서 읽는 것 — 00:25–00:30

[실제 적재 SQL](../../flink/ingest.sql.template)의 `kafka_events`를 함께 읽습니다. `format='raw'`는 Kafka value를 `payload STRING` 한 컬럼으로 받습니다. 이 단계에서 `before`·`after`를 풀거나 업무 키별 현재 상태를 만들지는 않습니다.

```sql
payload STRING,
topic STRING METADATA FROM 'topic' VIRTUAL,
partition_id INT METADATA FROM 'partition' VIRTUAL,
kafka_offset BIGINT METADATA FROM 'offset' VIRTUAL,
kafka_ts TIMESTAMP_LTZ(3) METADATA FROM 'timestamp' VIRTUAL
```

`METADATA FROM`은 Kafka가 제공하는 토픽·파티션·offset·timestamp를 읽는 선언입니다. `VIRTUAL`은 이 컬럼을 원본 Kafka 테이블의 쓰기 대상에서 제외한다는 뜻입니다. 뒤의 SELECT로 값을 명시해 보내면 Bronze의 일반 컬럼에 저장할 수 있습니다. Kafka timestamp를 원천 DB의 commit 시각으로 간주하지 않습니다.

`scan.startup.mode='earliest-offset'`은 복원할 상태가 없을 때 보관된 가장 이른 위치에서 읽기 시작한다는 설정입니다. checkpoint에서 복원할 때는 저장된 처리 위치를 사용하며, 재시작할 때마다 무조건 처음부터 읽는다는 뜻은 아닙니다.

### Flink는 변경 이력을 추가합니다 — 00:30–00:35

출력 SQL에서 무엇을 남기고 무엇을 제외하는지 읽습니다.

```sql
INSERT INTO lake.bronze.cdc_events
SELECT payload, topic, partition_id, kafka_offset, kafka_ts, CURRENT_TIMESTAMP
FROM kafka_events
WHERE payload IS NOT NULL;
```

필터가 제외하는 것은 Kafka value 전체가 null인 tombstone입니다. 삭제 이벤트 `op=d`는 `after=null`이어도 JSON 본문이 있으므로 남습니다. 이 INSERT SELECT는 **변경 이력을 append**하며 업무 키로 기존 행을 덮어쓰는 upsert가 아닙니다. 전달 위치와 Flink 처리 시각도 원문과 함께 보존합니다. `CURRENT_TIMESTAMP`로 채운 `ingested_at`은 원천 DB나 Iceberg 테이블의 commit 시각이 아닙니다.

이력·현재 상태·지표의 책임을 나누면 Flink가 여기서 하지 않는 일도 분명해집니다. 세 계층은 모두 Iceberg 테이블로 관리할 수 있습니다.

| 계층 | 내 설계에서 답할 질문 |
|---|---|
| Bronze 이력 | 어떤 변경을 받았고 다시 해석할 근거가 남아 있나요? |
| Silver 현재 상태 | 같은 키의 늦거나 반복된 변경에서 현재 값을 어떻게 고르나요? |
| Gold 지표 | 집계 단위·기준 시각·취소 처리 규칙은 무엇인가요? |

오늘은 Flink의 입력·필터·출력을 읽고 내 설계의 보존 정보를 정합니다. 현재 상태를 만드는 Spark MERGE와 지표를 만드는 dbt 모델 작성은 후속 회차에 둡니다.

### Iceberg 기본 구조 — 00:35–00:40

Iceberg는 저장소의 파일을 테이블로 관리하는 형식입니다. 이번에는 다음 세 역할만 연결해봅니다.

| 구성 | 맡는 역할 | 이 프로젝트에서의 위치 |
|---|---|---|
| Catalog | 테이블 이름에서 현재 metadata 파일의 위치를 찾음 | 별도 PostgreSQL `catalog-db`의 JDBC Catalog |
| Metadata | 스키마·snapshot과 읽을 파일을 찾는 정보를 관리 | S3 호환 저장소의 메타데이터 파일 |
| Data | 실제 행을 저장 | S3 호환 저장소의 Parquet 파일 |

snapshot은 **테이블의 일관된 상태**를 나타냅니다. snapshot을 만들 때마다 전체 데이터를 복사한다는 뜻은 아닙니다. Flink와 Spark가 같은 Catalog를 사용하는 이유도 같은 테이블의 현재 metadata 위치를 따라가기 위해서입니다. [공식 설명: JDBC Catalog](https://iceberg.apache.org/docs/1.10.0/jdbc/), [Reliability](https://iceberg.apache.org/docs/1.10.0/reliability/).

### 파일 저장과 테이블 commit — 00:40–00:45

쓰기에 필요한 새 Data·Metadata 파일을 준비한 뒤, Catalog의 현재 metadata 참조를 원자적으로 바꾸는 것이 테이블 commit의 핵심입니다. 최신 테이블 상태를 확인하는 새 조회는 커밋된 snapshot을 기준으로 읽습니다. 저장소에 파일이 생겼다는 사실과 그 파일이 테이블 조회에 반영됐다는 사실을 구분합니다. [공식 설명: Reliability](https://iceberg.apache.org/docs/1.10.0/reliability/).

checkpoint는 Flink의 처리 위치·상태를 복구하기 위한 지점이고, commit은 Iceberg 테이블 상태를 바꾸는 경계입니다. 두 ID를 일대일로 맞추지 않으며, 이번 변경이 보이는지는 실제 SELECT로 확인합니다. 이 차이는 두 번째 짧은 실험에서 다시 읽습니다. [공식 설명: Flink Writes](https://iceberg.apache.org/docs/1.10.0/flink-writes/).

Bronze의 `op=d`는 삭제 사건을 담은 일반 데이터 행입니다. Iceberg의 행 삭제 처리를 위한 Delete File과 다릅니다. Manifest의 세부 계층, CAS, CoW·MoR, 파일 정리와 튜닝은 후속 회차에서 다룹니다. 이번에는 구조와 조회 경계를 이해하고 기존 학습지의 저장 책임·관찰 질문에 한 줄로 연결합니다.

## 3. 짧은 실험 1 — 필터와 append가 설계대로 남겼을까?

강사가 생성·정정·삭제가 끝난 공통 환불 키 하나를 읽습니다. 실행 전에 질문에 답해보세요.

> Flink가 tombstone을 제외하고 변경을 append했다면, 삭제 뒤 원천과 Bronze에는 무엇이 남아야 할까요?

원천 행과 같은 키의 Bronze `op`·수정 전후 값을 비교합니다. 준비된 공통 예제에서는 삭제 뒤 원천 0행과 Bronze c/u/d 세 이력을 기대하지만, 실제 출력과 구분해 읽습니다. `op=d`가 남은 결과를 앞의 필터와 연결합니다. 이력 행 수가 현재 업무 건수와 같아야 하는 것은 아닙니다. 특정 키를 읽은 건수를 전체 테이블이나 모든 재처리 상황의 보장으로 확대하지 않습니다.

관찰 뒤에는 학습지에 현재 상태를 만들 규칙의 초안을 적습니다.

- 어느 키가 현재 상태 한 건인가요?
- 삭제되었다는 사실은 어떻게 반영하나요?
- 같은 키의 오래되거나 반복된 변경을 무엇으로 판단하나요?

공통 구현의 LSN·offset 순서 기준은 단일 원천과 토픽별 단일 파티션 전제입니다. 모든 이벤트의 전역 순서를 뜻하지 않습니다. 내 주제에 필요한 버전 정보가 아직 모호하면 보류 질문으로 남깁니다.

## 4. 짧은 실험 2 — Kafka에 있으면 Bronze에서도 읽힐까?

강사가 준비한 새 공통 키에서 변경 하나만 관찰합니다. 먼저 Kafka에 보인다는 사실만으로 Bronze에도 이미 반영됐다고 말할 수 있을지 생각합니다. Flink의 계속되는 입력 소비, checkpoint, Iceberg commit, 실제 SELECT를 구분하며 같은 키·변경의 Kafka 위치와 Bronze 결과를 대조합니다.

checkpoint는 처리 위치와 상태의 복구 지점이고, Iceberg commit은 테이블이 참조하는 저장 상태와 관련됩니다. checkpoint ID와 snapshot ID를 일대일로 맞추지 않습니다. 상태 화면만으로 특정 키가 읽혔다고 판단하지 않고 실제 행을 확인합니다.

변경이 너무 빨리 도착해 중간 상태를 못 볼 수도 있습니다. 이때 없었던 지연을 연출하지 않습니다. 반영이 늦어지면 어디까지 확인됐는지 말하고 준비 증거와 구분합니다. 시연을 위해 설정을 바꾸거나 복구 실험을 추가하지 않습니다.

관찰 뒤에는 앞서 정한 두 지연 목표의 **시작 기준과 끝의 SELECT**를 적습니다. 실제 원천 commit 시각을 확보하지 않았다면 관찰 시작부터의 시간이라고 구분합니다. helper의 `wait_observed_seconds`도 wait 시작부터 첫 Bronze 관측까지이며 원천 commit부터의 전체 지연이 아닙니다. 오늘 Gold 갱신이나 목표 지연 달성을 실험한 것으로 적지 않습니다.

## 5. 개인 도메인·테이블 설계 확정 — 30분

앞에서 적은 내용을 바탕으로 다음 두 가지에 집중합니다.

1. **원천과 적재 설계 확정:** 도메인, 테이블 2~3개의 이름·한 행의 의미·PK/FK, 수정·삭제의 의미를 정합니다. Kafka 토픽을 나눌 기준과 이름, Bronze에 남길 원문·전달 정보와 선택 이유도 학습지에 적습니다.
2. **변경 사례와 확인 기준:** 신규·수정·삭제를 작은 값으로 표현하고, 같은 변경을 다시 받았을 때 유지되어야 할 값 하나와 확인할 테이블·키 조건·결과를 적습니다. 실제 DDL이나 복잡한 SQL 문법을 완성하는 것은 오늘의 필수 작업이 아닙니다.

시간이 남으면 과거 날짜의 정정을 추가로 생각합니다. 도메인·원천 테이블과 Flink 입력·Bronze 보존 정보는 이번 회차에 확정하고, 근거가 부족한 최신 순서 규칙이나 지연 목표는 보류 이유와 다음 질문을 남깁니다. 빈칸을 채우려고 가정한 값을 실측으로 적지 않습니다.

## 6. 설계 리뷰와 수업 후 이어갈 것

서로의 업무 질문과 선택 이유를 짧게 듣고 키·삭제·재전달·지연·검증 증거 중 하나를 질문합니다. 도구를 더 넣기보다 어떤 규칙이 필요한지, 무엇을 확인하면 판단할 수 있는지 묻습니다. 짝 구성이 어렵다면 두 사례를 전체가 함께 리뷰합니다. 별도 발표 자료는 필요하지 않습니다.

수업 후에는 확정한 도메인·원천 관계·토픽·Bronze 보존 정보를 정리하고, 다음 Silver 구현에 넘길 키·삭제 처리·최신 상태 기준과 기대값을 남깁니다. 공통 예제가 궁금한 부분은 [개인 실행 안내](../../docs/self-study.md)로 다시 확인할 수 있습니다. 실행 도우미를 통과한 결과가 개인 프로젝트 설계를 대신하지는 않습니다.

제출 방법과 기한은 공지를 따릅니다. 8회차까지는 스터디 수업이고 최종 발표는 별도 일정입니다.
