# 4회차 개인 Silver 설계 학습지

이번 주에 정리하는 도메인·원천 테이블 DDL·관계·변경사례 초안에서 **한 테이블**을 골라 작성합니다. 개인 주제를 공통 주문 예제로 바꾸는 활동이 아닙니다. 약 20분 동안 핵심 규칙과 SQL 초안을 만들고, 이어지는 7분에 동료와 확인합니다. 처음 12분은 **한 행·키 / 버전·삭제 규칙 / 후보 SQL 뼈대**를 우선 적고, 나머지 8분에 상세 타입·MERGE·기대값을 확장합니다.

작성 순서는 [학생 가이드의 Silver 설계 순서](student-guide.md#silver-설계-순서)와 같습니다. 단계마다 답, 그 답의 근거, 그 답이 깨지는 조건을 함께 적습니다. 0절과 7절은 수업 뒤 개인 구현 때 채웁니다.

수업 중 별도 제출 양식을 새로 만들거나 전체 개인 파이프라인을 완성할 필요는 없습니다. 실행했다면 실제 결과를, 아직 실행하지 않았다면 기대값과 확인할 정보를 구분해 적습니다. 제출 방법과 기한은 공지를 따릅니다. 최종 발표는 8회 스터디 이후 별도 일정입니다.

## 공통 예제의 작성 기준

| 항목 | 공통 환불 예시 |
|---|---|
| 한 행·키 | 한 환불의 현재 상태 / refund_id |
| 원천 관계 | refunds.payment_id → payments.payment_id. 같은 결제에 여러 환불 가능 |
| 순서 | 이 실험의 단일 원천·고정 토픽·파티션 0에서 숫자 LSN 우선, 같은 LSN이면 offset |
| 삭제 | 환불 철회. before의 키·값과 삭제 버전을 남기고 유효 조회에서 제외 |
| 선택·MERGE | PK별 최신 후보 하나 / 대상보다 새 버전만 UPDATE / 없는 키 INSERT |
| 최종 검증 | 현재 snapshot의 보존 한 행·is_deleted=true·LSN300·offset12 / 유효 환불 0행 |

고정 LSN 100/200/300과 offset 10/11/12는 수업용 fixture입니다. 자기 도메인의 전역 순서 규칙으로 그대로 가져오지 않습니다. 삭제 표시 행의 amount=30000은 철회 직전 값이며 현재 유효 환불액이 아닙니다.

## 4. 정규화·최신 후보 SQL 초안

다음은 구조를 읽기 위한 의사 SQL입니다. `<...>`를 자신의 스키마·규칙으로 바꾸고 타입·동일 버전 정책을 먼저 결정합니다. 그대로 실행하는 공통 정답이 아닙니다. 공통 실습의 실행 SQL은 [01-latest.sql](sql/01-latest.sql)에 있습니다.

```sql
WITH normalized AS (
  SELECT
    <before 또는 after에서 고른 PK> AS entity_id,
    <타입을 확인한 업무 컬럼>,
    <삭제 여부> AS is_deleted,
    <숫자형 또는 검증된 원천 버전> AS source_version,
    <비교 가능한 범위의 전달 순서> AS delivery_order
  FROM <내 Bronze 입력>
  -- PK·버전·타입·전달 정보의 오류는 어떻게 중단·기록할지 별도로 정합니다.
), ranked AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY entity_id
    ORDER BY source_version DESC, delivery_order DESC
  ) AS rn
  FROM normalized
)
SELECT * FROM ranked WHERE rn = 1;
```

- 잘못된 입력을 찾는 조건과 기록할 정보:
- 후보 SELECT에서 먼저 확인할 컬럼·키:
- `DISTINCT`·금액 MAX로 대신하면 틀리는 작은 반례:

## 5. MERGE 조건 초안

```sql
MERGE INTO <내 Silver> AS t
USING <검증한 최신 후보> AS s
ON t.entity_id = s.entity_id
WHEN MATCHED AND (
  <입력이 대상보다 새 버전인 조건>
)
THEN UPDATE SET <업무 컬럼·삭제 여부·버전>
WHEN NOT MATCHED THEN INSERT <필요한 컬럼과 값>;
```

- ON이 식별하는 같은 엔티티:
- 과거 입력을 거절하는 조건:
- 삭제 뒤 새 INSERT가 실제로 가능한 도메인인지:
- 대상의 키 중복·누락을 찾는 조회:
- 같은 입력을 다시 적용해도 같아야 하는 업무 값:

**확인 질문:** 여러 후보가 같은 대상 행을 갱신하지 않나요? 버전 가드 없이 도착 순서대로 덮고 있지는 않나요?

## 6. 기대값과 실제 확인

확인 기준은 ①PK 한 행 ②최신 버전 ③삭제 유지 ④동일 입력의 업무 결과 유지 ⑤무효 입력의 실행 중단입니다. 아래 입력 사례별 기대와 별도로, 키·버전이 잘못됐을 때의 중단·기록 방식을 적습니다.

작은 숫자로 먼저 작성합니다. 자신의 삭제 정책이 공통 예제와 다르면 행 수·필터 기대도 그 정책에 맞게 바꿉니다.
